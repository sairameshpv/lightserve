# lightserve vs vLLM -- Locust load test

`locustfile.py` load-tests either server's OpenAI-compatible
`POST /v1/completions` (lightserve's own `server/app.py`, or a real vLLM
server -- see `nebius_setup_commands.txt`'s `docker run vllm/vllm-openai`
command) with the same closed-loop task shape, so a run against each at the
same concurrency is a same-hardware, same-request-pattern comparison. See
`locustfile.py`'s module docstring for the full design (why `--target`
exists, why there are two prompt files, why `wait_time = between(0, 0)`).

Run matrix this benchmark cares about: 10 and 50 concurrent users, against
each server, on the same GPU box (bring each server up on its own port, or
one at a time on `:8000` -- `server/README.md`'s "Running it" section and
`nebius_setup_commands.txt` step 7, respectively):

```bash
pip install locust

# lightserve, 10 and 50 concurrent users
locust -f benchmarks/locustfile.py --host http://localhost:8000 \
    --headless --users 10 --spawn-rate 10 --run-time 2m \
    --target lightserve --csv benchmarks/locust_lightserve_10
locust -f benchmarks/locustfile.py --host http://localhost:8000 \
    --headless --users 50 --spawn-rate 50 --run-time 2m \
    --target lightserve --csv benchmarks/locust_lightserve_50

# vLLM, same two concurrency levels
locust -f benchmarks/locustfile.py --host http://localhost:8000 \
    --headless --users 10 --spawn-rate 10 --run-time 2m \
    --target vllm --csv benchmarks/locust_vllm_10
locust -f benchmarks/locustfile.py --host http://localhost:8000 \
    --headless --users 50 --spawn-rate 50 --run-time 2m \
    --target vllm --csv benchmarks/locust_vllm_50

# then, per concurrency level:
python3 benchmarks/compare_locust_runs.py \
    --a benchmarks/locust_lightserve_10 --a-label lightserve \
    --b benchmarks/locust_vllm_10       --b-label vllm
```

Each `locust ... --csv <prefix>` run writes `<prefix>_stats.csv`,
`<prefix>_stats_history.csv`, `<prefix>_failures.csv`, and
`<prefix>_exceptions.csv` -- `compare_locust_runs.py` reads the first two;
the other two are worth checking by hand if `Failures` is nonzero.

## Files

- `locustfile.py` -- the load test itself (see its module docstring).
- `token_prompts.jsonl` -- lightserve's prompt set: token ids, generated by
  `generate_token_prompts.py` as a length-matched (not content-matched --
  there's no tokenizer to match content against, see that script's module
  docstring) companion to `baseline_prompts.jsonl`'s real text prompts,
  which vLLM's `--target vllm` run uses directly.
- `compare_locust_runs.py` -- prints a side-by-side table (requests,
  failures, throughput, p50/p95/p99/max latency) from two `--csv` runs.

## What this isn't

Not an apples-to-apples *quality* comparison -- lightserve has no
tokenizer and random (not real-checkpoint) weights (see
`model/minimal_llama.py`'s module docstring), so its outputs are
meaningless as text; only the vLLM run's output is real generation. This
benchmark only compares serving-engine *mechanics* under concurrent load
(admission/scheduling/streaming latency, throughput, failure rate) at a
matched prompt-length and `max_tokens` distribution -- not generation
quality, and not (yet) matched hardware utilization (that's
`benchmarks/profiling/`'s job, see `benchmarks/profiling/report.md`).
